## 1. Executive summary

Рекомендация: B — нужен ограниченный набор исправлений. Оснований для второго широкого этапа декомпозиции по #187 сейчас недостаточно.

Первый рефакторинг создал полезные границы: ресурсы соединения имеют отдельного владельца, authoritative состояние сосредоточено в Redux, игровые команды проходят несколько уровней проверки, а существенная часть доменной маршрутизации уже вынесена из LobbyRuntime.

Основные найденные проблемы находятся на стыках этих границ: между сетевым pending и локальным Rewind, между terminal bootstrap failure и presentation, между отклонением игрового события и решением продолжать доверять локальному состоянию. Дополнительное разбиение классов само по себе их не устранит.

### Три наиболее важные проблемы

1. Подтверждено: вход в Rewind очищает pending уже отправленного игрового действия. После возврата в Live до получения серверного результата можно отправить ещё одно действие. Это нарушение клиентской защиты от повторной отправки, хотя не автоматический replay после reconnect.

2. Подтверждено: неудачный bootstrap оставляет пользователя в загрузке без доступного восстановления. Runtime уже перешёл в failed, но App продолжает показывать «Loading game…».

3. Потенциальный риск: отказ применить событие текущей игры не прекращает доверие к локальному состоянию. Ошибка reduction записывается в диагностику, а сессия остаётся READY. Не доказано, что это происходит на production; существующий тест подтверждает сам путь отказа, но не проверяет последующие события и команды.

Точные доказательства и ограничения приведены в разделе 3.

### Три сильные стороны

1. Хорошая модель владения соединением. ConnectionRuntime сочетает монотонный epoch с проверкой идентичности владельца, инвалидирует ownership до disposal, закрывает поздно созданные сокеты и поддерживает single-flight. Это содержательная защита от гонок, а не декоративная декомпозиция. ConnectionRuntime.ts, 154–217

2. Правильный основной путь игровых команд. Проверяются текущая READY-комната, роль, режим, ход, pending и допустимость действия; successful send не изменяет authoritative GameState оптимистически. Прикладной очереди повторной отправки нет. GameplayRuntime.ts, 200–275, ConnectionRuntime.ts, 131–151

3. Существуют серьёзные поведенческие и интеграционные тесты. Они проверяют stale callbacks, порядок welcome/recovery, partial send, перестановки событий rematch и отсутствие command replay. Главный пробел — композиция runtime с реальными presentation-переходами, а не отсутствие тестирования вообще. ConnectionRuntime.test.ts, 226–307, GameplayRuntime.test.ts, 270–298

## 2. Фактическая архитектурная карта

### 2.1. Кто чем владеет

| Компонент | Фактическое владение | Архитектурная оценка |
|---|---|---|
| Сервер | Игровая истина, подтверждённое attendance, история действий | Основной авторитет сохранён |
| sessionSlice, lobbySlice | Наблюдаемая фаза соединения, authenticated user, серверные настройки, пользователи и столы | Проекции серверного состояния |
| roomSlice | Комната, роль, принятый clientState, load identity, pending gameplay/attendance/restart/hypothetical | Главный владелец состояния комнаты и локальных намерений |
| historySlice, chatSlice, sessionMessagesSlice, terminationSlice | История и запросы, сообщения/черновики/read state, session-local conversations, vote state | Доменные состояния остаются в store |
| ConnectionRuntime | Socket, listeners, welcome/retry timers, opening promise, epoch, retry policy, app activity | Правильный владелец непереносимых ресурсов |
| GameBootstrapCoordinator | Активная загрузка, её epoch, watchdog, промежуточные metadata/clientState | Временное владение до публикации результата в Redux |
| TableManagementRuntime | Временный контекст создания стола с ботами, включая секрет для приглашения | Обоснованное transient state вне Redux |
| Gameplay / Replay / History / Attendance runtime | Командная политика, обработка событий, side effects через переданные возможности | Отдельных конкурирующих копий authoritative игры нет |
| ChatRuntime | Реестр локальных команд и их исполнение | В основном обработчик команд, а не полный владелец chat domain |
| App.tsx, C17 presentation | Focus, browsing origin, открытые задачи, выбранные карты, формы и локальные interaction state | Должны оставаться отделёнными от attendance и сетевых pending |

Основания: roomSlice.ts, 27–70 и 107–148, ConnectionRuntime.ts, 44–74, GameBootstrapCoordinator.ts, 137–198, TableManagementRuntime.ts, 20–44.

Здесь важно различать два вида состояния. ConnectionRuntime.ready описывает пригодность принадлежащего ему транспорта; session.phase — наблюдаемое состояние приложения. Это не доказанное вредное дублирование. Их согласованность обеспечивается порядком обработки welcome и совместной проверкой в isReady().

Аналогично, bootstrap временно строит будущий GameState, но не публикует его как готовую игру до завершения обязательных стадий. Создание дополнительного GameRuntime со своей постоянной копией состояния сейчас скорее добавит второго владельца.

### 2.2. Маршруты событий и команд

Входящий путь:

1. NetworkSocket вызывает listener, принадлежащий ConnectionRuntime.
2. Проверяется актуальность owned connection.
3. LobbyRuntime.onMessage() декодирует frame.
4. Событие направляется в доменный runtime, bootstrap или междоменную ветку orchestrator.
5. Redux принимает изменение с соответствующими проверками контекста.
6. UI читает store через selectors.

Обработка WebSocket frame здесь синхронная: между получением frame и его основной обработкой нет await и отдельной конкурентной очереди. Поэтому механическое введение async event bus может ухудшить важное существующее свойство. ConnectionRuntime.ts, 203–217, LobbyRuntime.ts, 489–547

Исходящий путь игровых действий:

1. UI вызывает facade.
2. Доменный runtime проверяет допустимость команды.
3. Encoder формирует protocol frame.
4. ConnectionRuntime.send() проверяет текущий READY socket.
5. Выполняется один socket.send().

Возврат true означает успешную передачу в локальный транспорт, а не подтверждение сервером игрового результата. Поэтому pending должен переживать любые локальные presentation-переходы.

Protocol boundary реализован через валидаторы, discriminated union ServerEvent и encoders. Отдельного реализованного слоя HanabClient, изображённого в старой архитектурной схеме, в этом пути нет. lobbyProtocol.ts, 660–725

### 2.3. Composition root и зависимости

application.ts уже является composition root верхнего уровня:

- создаёт HanabNetworkSession;
- создаёт raw LobbyRuntime с store;
- оборачивает facade в runtimeCommandGate;
- создаёт TerminationRuntime с raw facade;
- создаёт ChatRuntime с gated facade и termination capability.

Сам LobbyRuntime конструирует внутренние collaborators. Получается двухуровневая композиция, но она явная и детерминированная. Доказательства необходимости переносить все new в один файл нет. application.ts, 9–38, LobbyRuntime.ts, 88–146

В проверенном графе runtime не обнаружен проблемный цикл value imports. Обратные callbacks вида «domain runtime вызывает переданный sender facade» — намеренная связь управления. import type и Pick<LobbyRuntime, ...> не создают runtime module cycle.

Наиболее широкая возможность — именно публичный:

`send(command: string, payload?: unknown)`

Его получают Chat и Termination. Замена Pick на интерфейс с тем же произвольным send почти ничего не изменит в безопасности. Полезное сужение должно ограничить допустимые операции, а не только переименовать тип. LobbyRuntime.ts, 198–200, ChatRuntime.ts, 31–39, terminationRuntime.ts, 5–9

Что имеет смысл заменить capability-интерфейсами:

| Зависимость | Разумное направление | Нужно ли сейчас |
|---|---|---|
| Chat → Pick<LobbyRuntime, ...> | Независимый контракт допустимых chat/table-command операций | При следующем содержательном изменении Chat |
| Termination → произвольный send | Узкая возможность terminate/vote; для отложенного подтверждения — ожидаемый контекст комнаты | После проверки риска старого Alert |
| Gameplay / Replay / Attendance → callbacks send/readiness | Уже узкие capabilities по существу | Массовая замена не нужна |
| History → два HTTP-метода | Уже ограниченный контракт | Оставить |
| Connection → openSocket и lifecycle callbacks | Уже подходящая граница | Оставить |

Небольшая factory для создания той же композиции с fake transport может понадобиться для тестов. Но сначала стоит использовать существующие возможности Jest. Новый ClientRuntime, DI container или общий RuntimeServices как service locator не оправданы.

### 2.4. Насколько перегружен LobbyRuntime

Он остаётся широким facade/orchestrator: команды, decode/routing, recovery, некоторые chat/settings операции, cross-domain переходы. Однако его собственные поля — преимущественно readonly ссылки на collaborators; socket/timers/retry state из него действительно удалены. LobbyRuntime.ts, 68–86

Моя оценка: широкий API есть, опасного монопольного владения всем состоянием уже нет. Это приемлемая промежуточная и, возможно, долговременная архитектура для данного клиента.

Что уже делегировано:

- History events → HistoryRuntime;
- Replay/Hypothetical → ReplayInteractionRuntime;
- notes → GameplayRuntime.

Это уже выполненная часть кандидатов #187. LobbyRuntime.ts, 676–721

Что следует оставить видимым в orchestrator:

- welcome → READY → recovery;
- game/joined и завершение pending create;
- tableStart → room transition → bootstrap;
- rematch/migration;
- warning/error cleanup;
- двойную обработку gameHistory: сначала History, затем bootstrap/finished-game path.

Последний порядок уже явно защищён интеграционным тестом. LobbyRuntime.test.ts, 4300–4309

Chat events можно когда-нибудь объединить с ChatRuntime, но сейчас это затронет bot echo filtering и определение комнаты во время join/create/rematch. Наивный перенос также создаст обратную зависимость Lobby → Chat при существующей Chat → Lobby. Текущей выгоды, оправдывающей этот перенос отдельным PR, я не вижу.

### 3.1. Подтверждено: presentation снимает сетевую неопределённость

Последовательность для первой проблемы:

1. Сейчас ход локального игрока.
2. play(order) проходит проверки, создаёт pendingGameplayAction, отправляет frame.
3. Серверный результат ещё не получен.
4. Пользователь входит в Rewind.
5. reviewSegmentSelected выполняет state.pendingGameplayAction = null.
6. Пользователь возвращается в Live.
7. Authoritative состояние ещё прежнее: тот же ход, карта ещё в руке, pending отсутствует.
8. Следующая команда снова проходит guard.

Ключевая строка находится в roomSlice.ts, 1140–1152. Возврат в Live выполняет replayExit, но утраченное pending не восстанавливает.

UI-путь доступен: Rewind отключён только при отсутствии истории; wrapper takeWorkbenchTask лишь очищает feedback и вызывает действие. C17GameScreen.tsx, 857–860, 1267–1277. Возврат осуществляется локальным reviewSegmentSelected({segment:null}). 406–416

Существующая защита: пока пользователь остаётся в Rewind, gameplay запрещён. Обычный второй send при сохранённом pending тоже запрещён.

Почему защиты недостаточно: локальный переход уничтожает сам факт незавершённой отправки.

Что доказано: повторный frame может быть отправлен по новому пользовательскому действию. Не доказано: сервер применит оба действия. Это также не нарушение запрета автоматического replay после reconnect — автоматического повтора здесь нет.

Минимальное исправление: presentation может снимать выбор карты и armed interaction, но не сетевой pending. Не требуется запрещать Rewind, менять GameState или вводить новый runtime.

Если ничего не менять, дефект останется особенно заметным при большой задержке ответа. Стоимость узкой правки с тестом существенно ниже стоимости общего рефакторинга.

### 3.2. Подтверждено: bootstrap failure безопасен для игры, но не завершён для пользователя

Последовательность:

1. welcome установил READY.
2. tableStart начал загрузку.
3. Не пришёл/не принят init или gameActionList; либо не удалось отправить loaded.
4. Watchdog или send failure вызывает fail(load).
5. Таймер снят, load и Redux bootstrap получили failed.
6. Комната осталась awaiting_game_bootstrap.
7. App безусловно показывает загрузку.

Runtime-часть подтверждается GameBootstrapCoordinator.ts, 597–605 и существующим тестом watchdog, 584–599. Presentation не различает фазы: App.tsx, 720–725.

При focus на комнате navigation/app bar скрыты, а Back для awaiting не выполняет полезного перехода. Следовательно, это не просто неверная подпись при доступной кнопке Retry. App.tsx, 302–315, 835–848

Существующая защита правильна: неудачная загрузка не публикуется как LIVE; loaded не считается отправленным при неуспехе; автоматического повторения игровых команд нет.

Недостаточность: пока транспорт остаётся READY и не происходит внешнего события, попытка закончилась, а пользовательский путь — нет.

Просто добавить кнопку, вызывающую connect(), недостаточно: при текущем READY соединении этот метод возвращается без новой попытки. ConnectionRuntime.ts, 154–159

Предпочтительное минимальное решение — явное состояние ошибки и операция новой authoritative synchronization через существующую границу invalidation/reconnect. Для Live восстановление должно опираться на welcome hints. Если сервер не возвращает resume-контекст для конкретного replay, корректным результатом может быть authoritative состояние без комнаты; нельзя обещать восстановление replay путём неявного повторения старого replayCreate.

### 3.3. Риск: после потери текущего action клиент остаётся пригодным к отправке команд

receiveIncrementalDetailed() перехватывает ошибку преобразования/reducer и возвращает reducer-failure. LobbyRuntime записывает диагностику и заканчивает обработку. Ветка не достигает общего catch ConnectionRuntime, который иначе инвалидировал бы соединение и запустил восстановление. GameBootstrapCoordinator.ts, 455–480, LobbyRuntime.ts, 515–539

Существующий тест уже содержит schema-valid событие, которое не удаётся применить, и проверяет сохранение прежнего состояния. GameBootstrapCoordinator.test.ts, 531–544

Защита: повреждённый результат reducer не публикуется.

Оставшийся риск: неизменённый предыдущий снимок может быть уже неполным относительно сервера. Следующие события будут применяться к нему, а domain command gate не знает, что доверие к потоку потеряно.

Это особенно заслуживает проверки после PR #195, где уже принято решение восстанавливать соединение после неожиданной ошибки обработки inbound события.

Нужна узкая policy: различать harmless stale/wrong-table rejection и невозможность применить событие подтверждённо текущей игры. Reconnect на любой неизвестный или malformed frame был бы чрезмерным и мог бы создать цикл восстановления из-за необязательного сообщения.

### 3.4. Риски устаревшего контекста: что epoch действительно гарантирует

Старое соединение. Защита сильная: identity + epoch, удаление listeners, stale-open disposal. Не нашёл основания менять её архитектуру.

Другая комната с явным tableID. Runtime/reducers обычно проверяют epoch и table ID; bootstrap дополнительно использует load epoch.

Старая загрузка того же tableID в той же connection. Здесь гарантия слабее, чем может показаться из unit-тестов. LobbyRuntime передаёт входящим init/history текущий currentGameLoadEpoch; wire frame не несёт этот локальный идентификатор. Поэтому прямой вызов coordinator со старым load epoch тестирует внутренний guard, но не доказывает происхождение реального frame. LobbyRuntime.ts, 656–666, GameBootstrapCoordinator.test.ts, 556–580

Replay-события без tableID. hypothetical и hypoAction получают table ID из текущей комнаты уже на клиенте. Это не восстановление provenance события. ReplayInteractionRuntime.ts, 321–350, lobbyProtocol.ts, 582–586

Это не доказательство текущей corruption. Последовательность отправки сервером и lifecycle комнаты могут исключать опасное пересечение. Нужны реалистичные raw-frame integration sequences и явно записанные предпосылки. Добавление локального epoch непосредственно при получении frame не решит отсутствие wire correlation.

Generic warning/error. Любое такое событие очищает pending gameplay вместе с pending других доменов. Возможный опасный случай — предупреждение другого запроса между отправкой action и его результатом. Текущий тест закрепляет очистку по warning, но не доказывает её корректность при конкурирующих запросах. LobbyRuntime.ts, 808–822, GameplayRuntime.test.ts, 314–323. До изменения нужно подтвердить серверную последовательность; нельзя придумывать request correlation по тексту ошибки.

### 3.5. Presentation, delayed callbacks и lifecycle

Разделение focus и attendance в целом реализовано правильно. Browse/Home изменяют focus, Return из собственного Rewind выполняет локальный review transition, а не leave/reattend. Скрытая комната сохраняется mounted с отключёнными pointer/accessibility paths. App.tsx, 163–182, 885–893

C17 disarms interaction при скрытии, background и смене load. Это нужно сохранить. C17GameScreen.tsx, 144–154, 197–214

Но runtime проверяет текущее состояние, что не всегда равнозначно проверке исходного намерения:

- Alert завершения игры создаётся в A.
- Пока он открыт, состояние может перейти через reconnect/rematch в готовую игру B.
- Callback вызывает terminateGame() без ожидаемого table/load.
- Runtime заново выбирает текущую B.

Guard отвергнет промежуточную, finished или replay-комнату, но другая уже готовая Live-комната его проходит. Native сохранение Alert при такой последовательности не воспроизводилось, поэтому это риск. Минимальное возможное исправление — ожидаемый контекст у отложенного подтверждения, а не общий command framework. TerminationControls.tsx, 41–52, terminationRuntime.ts, 29–42

Для background/foreground выбрана политика сохранения здорового READY socket. Если приходит close/error, восстановление предусмотрено. Не проверен физический случай, когда Android оставляет JS socket в OPEN без своевременного close/error, хотя транспорт уже непригоден. Принудительный reconnect на каждый foreground до получения такого evidence не рекомендую. ConnectionRuntime.ts, 100–115

Ещё одна граница вне socket epoch — HTTP auth probe: поздний missing без generation check вызывает reset сессии. Обычный UI ограничивает пересечения, поэтому достижимый пользовательский сценарий не подтверждён. Проверить deferred response разумнее, чем сразу выделять AuthRuntime. LobbyRuntime.ts, 157–160, App.tsx, 214–250

### 3.6. Replay/Hypothetical и command gate

Здесь важно не смешивать разные механизмы.

runtimeCommandGate — ограничитель команд для scenario gallery, а не основная защита Live от Replay. Реальная защита режимов находится в domain runtimes.

Solo Hypothetical применяет локальные действия. Shared Hypothetical отправляет replay-команды, предварительно валидирует набор, сохраняет pending до authoritative echo и не переотправляет частично отправленную операцию. Это правильная обработка неопределённости. ReplayInteractionRuntime.ts, 72–85, 218–272

Подтверждённого выхода из gallery в реальные игровые команды не найдено. Хотя Termination использует raw facade, gallery рендерит GameScreen со своим store без room children, содержащих Chat/Termination. Все найденные прямые C17 runtime calls входят в blocklist. GameplayScenarioGallery.tsx, 23 и 52–55

Однако проверка состава blocklist через regex не заменяет поведенческую проверку реальной композиции.

## 4. План небольших PR

Рекомендую три обязательных PR после фиксации результатов физического RC3 baseline. Четвёртый — только по результату проверки конкретной failure policy. Переименование и перестройка каталогов в этот этап не входят.

### PR 1. Сохранить pending gameplay при локальном Rewind

Цель: presentation не должна отменять неопределённость уже отправленной команды.

Модули: roomSlice, существующие gameplay/replay integration tests.

Точная граница: убрать очистку pendingGameplayAction из локального review-перехода. Сохранить существующие корректные пути очистки при server turn, connection boundary и завершении соответствующего контекста.

До/после: тест send → Rewind → Return Live → повторный send до turn; затем вариант с authoritative turn во время Rewind и вариант с reconnect.

Приёмка:

- До authoritative результата отправлен ровно один gameplay frame.
- Rewind доступен и не посылает gameplay.
- После результата eligibility определяется актуальным состоянием.
- Reconnect не воспроизводит старый action.

Главный риск: случайно сохранить pending там, где он уже должен завершиться. Поэтому тестировать не только блокировку, но и корректное освобождение.

Зависимости: только зафиксированный baseline.

Почему это выгодно: маленькая коррекция ownership устраняет доказанный дефект. Запретить Rewind при pending было бы более грубым обходом с ненужным изменением пользовательского поведения.

### PR 2. Завершить recovery для bootstrap.failed

Цель: терминальная ошибка загрузки должна иметь явный безопасный путь продолжения.

Модули: GameBootstrapCoordinator, LobbyRuntime/существующая connection boundary, App.tsx, room presentation, соответствующие тесты.

Точная граница:

- Различать loading и failed bootstrap.
- Дать одно явное действие authoritative resynchronization.
- Инвалидировать текущий failed context через существующий механизм владения ресурсами.
- Восстанавливаться по новому welcome и серверному контексту.
- Не сохранять очередь команд и не повторять прежние gameplay/replay-create intentions.

До/после: waiting-init timeout, waiting-history timeout, failed loaded, затем явное восстановление; отдельно вызов старого timer/socket callback после новой попытки.

Приёмка:

- Failed не отображается бесконечной активной загрузкой.
- Recovery действительно начинает новую попытку, а не вызывает READY connect() без эффекта.
- LIVE публикуется только после полного bootstrap.
- Если сервер не подтверждает прежнюю комнату, приложение приходит в корректное состояние без неё.
- Нет implicit leave/unattend и повторения игровых действий.

Главный риск: начать повторный bootstrap на том же сокете и переоценить защиту локального load epoch. Новая connection generation предоставляет более понятную границу без изменения wire protocol.

Зависимости: PR 1 технически не обязателен, но последовательное включение упрощает оценку регрессий.

Меньшая альтернатива: только показать текст ошибки. Она не решает отсутствие доступного recovery и поэтому недостаточна.

### PR 3. Защитить реальные App/runtime стыки и обновить карту архитектуры

Цель: покрыть поведение, которое сейчас в основном закреплено текстом исходников.

Модули: тесты App/presentation/gallery/application; docs/ARCHITECTURE.md.

Точная граница: несколько поведенческих harness-тестов с real store, real runtime и fake transport:

- Browse → inbound update → Return;
- reconnect/rematch при browsing focus;
- scenario suppression с отдельным scenario store и реальным production runtime graph;
- доступность recovery из PR 2.

Для этих проверок не следует mock-заменять сам runtime, чьи sends требуется наблюдать. Native UI dependencies можно изолировать существующим тестовым подходом.

Приёмка:

- Навигационные переходы не генерируют attendance/gameplay frames.
- Скрытая selection не становится вновь armed после Return.
- Scenario commands не меняют реальную комнату и не отправляют реальные frames.
- После закрытия gallery suppression освобождается.
- Документ описывает текущих владельцев, порядок событий и область действия epoch.

Риски: тестовый harness может стать чрезмерно связанным с JSX. Assertions должны наблюдать состояние, доступные действия и sends, а не внутреннюю форму компонентов.

Зависимости: PR 1 и PR 2, чтобы закреплять уже исправленное поведение.

Нужно ли менять composition root: только если тестирование существующих exports практически невозможно без небольшого seam. Допустима factory, возвращающая ту же композицию; перенос ownership, новый service locator и переименование facade не входят в PR.

Стоимость против долга: несколько целевых integration tests дешевле массового переноса сотен существующих assertions. Переписывать весь source-contract suite не нужно.

### Условный PR 4. Отзывать доверие после невозможности применить событие текущей игры

Условие начала: тест со schema-valid текущим gameAction, failure reduction и последующей попыткой send подтверждает продолжение команд на снимке с пропущенным событием; отдельно принимается требуемая fail-closed policy.

Цель: сделать потерю применимости authoritative потока явной.

Граница: только ошибка применения события, достоверно относящегося к текущей игре. Stale/wrong-table события продолжают безопасно игнорироваться; unknown optional messages не вызывают reconnect автоматически.

Модули: bootstrap incremental handling, orchestrator, существующая connection recovery; без нового event bus.

Тесты: отказ текущего action → команды закрыты → восстановление из истории; old-context failure не инвалидирует новую комнату; старые команды не повторяются.

Риск: излишне широкий критерий может вызвать reconnect loop. Поэтому этот PR нельзя подменять правилом «любая ошибка протокола перезапускает соединение».

Этот пункт не является обязательной «декомпозицией #187». Это отдельное решение о runtime safety, которому нужны собственные критерии.

## 5. Качество тестирования и минимальные недостающие сценарии

### Что уже покрыто хорошо

По инвентаризации в репозитории 134 test-файла; 46 содержат чтение исходников. Это не означает 46 чисто текстовых наборов: часть смешивает source assertions и поведенческие проверки. В runtime таких файлов только один; основная концентрация source-contract тестов — UI.

| Категория | Реальное содержание | Ограничение |
|---|---|---|
| Чтение текста исходников | Проверки наличия guards, absence runtime calls, формы JSX и gate list | Не доказывают фактическое выполнение effect/callback |
| Unit/domain behavior | Реальные reducers/store, injected send/readiness, protocol parsing | Изолированный collaborator может не видеть ошибку композиции |
| Runtime integration | Реальный LobbyRuntime, decoder, collaborators и Redux; fake только транспорт | Не воспроизводит native delivery и App rendering |
| Sequence/recovery | Stale callbacks, timers, partial send, rematch ordering, восстановление истории | Часть sequence tests вручную передаёт контекст, которого нет в wire frame |

Хороший пример unit-подхода — GameplayRuntime.collaborator.test.ts: реальный store/bootstrap, mock только sender и readiness. Строки 11–55

LobbyRuntime.test.ts использует fake socket, а не fake runtime. Поэтому его размер сам по себе не причина переносить тесты. Строки 40–85

Особенно показателен найденный дефект Rewind: отдельно есть тест one-shot pending и отдельно тест возврата из review. Оба проходят, а их композиция ошибочна. GameplayRuntime.test.ts, 246–268, 325–347

### Десять наиболее полезных недостающих тестов

Это набор по убыванию практической ценности. Для рисковых сценариев тест сначала должен установить достижимость и правильный контракт; не следует закреплять произвольную новую policy только ради зелёного результата.

| № | Последовательность | Что наблюдать |
|---|---|---|
| 1 | Gameplay send → Rewind → Return Live → новый send до ответа | Один outbound action; pending сохранён |
| 2 | Send → Rewind → authoritative turn / reconnect → Return | Корректное завершение pending; отсутствие replay; eligibility из нового состояния |
| 3 | Bootstrap timeout или failed loaded → failed UI → явный recovery → history | Доступное действие; новая попытка; LIVE только после handshake |
| 4 | Schema-valid current action не применился → следующий event → gameplay send | Явное решение о доверии к потоку; отсутствие незаметного продолжения на пропущенной истории |
| 5 | Gameplay pending + предупреждение другого запроса | Проверка, обоснованно ли снимается gameplay pending; без выдуманной request correlation |
| 6 | Повторный same-table bootstrap через raw socket frames | Проверять реальный adapter path, без искусственного old load epoch в wire |
| 7 | Сохранённый callback Terminate из A → готовая B → вызов callback | Команда не должна неожиданно адресоваться B |
| 8 | Mounted App: выбор действия → Browse → входящие изменения → Return; вариант с reconnect | Ноль gameplay/leave/unattend sends от навигации; interaction не rearmed |
| 9 | Реальная application composition + scenario store + gallery mount/unmount | Ноль sends в production socket при suppression; корректное освобождение lease |
| 10 | Старый HTTP probe завершается после нового lifetime или unmount | Старый результат не очищает актуальную сессию и не возобновляет оставленное ownership |

Отдельно физический RC3 gate должен проверить silent half-open: потерю сети в background, длительную паузу, восстановление сети и запаздывающие native close/error. Unit-тест может закрепить выбранную policy, но не доказать поведение Android transport.

Не нужно повторно добавлять общие тесты «OPEN ещё не READY», «старый socket callback игнорируется» и «partial hypothetical send не replay после reconnect»: содержательное покрытие этих случаев уже существует.

## 7. Stop conditions

Рефакторинг можно остановить, когда выполнены следующие условия:

1. Исправлены два подтверждённых P1: pending переживает локальный review, failed bootstrap имеет доступное authoritative recovery.
2. Составные сценарии закреплены поведением: проверяются реальные store/runtime/sends, включая presentation-переходы и gallery suppression.
3. Сохраняются основные инварианты: отсутствие автоматического replay gameplay, отбрасывание старых connection callbacks, отсутствие implicit attendance changes и разделение live/replay/hypothetical команд.
4. Физический baseline подтверждает выбранную lifecycle policy либо найденные отклонения выделены в отдельные конкретные defect tasks.
5. Граф владения можно объяснить без предположений: у ресурсов соединения, загрузки и принятых доменных состояний есть понятные владельцы; ограничения wire correlation записаны честно.
6. Нет воспроизводимого дефекта или ближайшей функции, требующих следующего структурного изменения.

Для остановки не требуется определённый размер LobbyRuntime, отсутствие callbacks, одинаковая структура каталогов или переименование всех классов под одну схему.

Документированный потенциальный риск не должен автоматически превращаться в бесконечный refactoring backlog. Но и отсутствие его в физическом smoke не доказывает невозможность: для важных рисков нужны целевые sequence checks, после которых принимается отдельное решение.

## 8. Финальная рекомендация

Выбираю B: ограниченный набор архитектурных исправлений.

Архитектурная основа уже достаточно здорова, чтобы продолжать развитие без глобальной переработки. ConnectionRuntime имеет обоснованную границу, domain runtimes не конкурируют за копии GameState, no-replay путь реализован явно, а attendance отделено от presentation.

При этом вариант C пока преждевременен: есть два конкретных дефекта, которые стоит исправить независимо от того, наблюдались ли они в обычной игре. Вариант A был бы чрезмерным: большая часть исходных направлений #187 уже реализована, а найденные ошибки не требуют новой системы runtime.

Практический следующий этап:

1. Зафиксировать результаты текущего физического RC3 baseline.
2. Исправить ownership pending при Rewind.
3. Завершить failed-bootstrap recovery.
4. Добавить несколько поведенческих проверок App/composition и привести архитектурную карту к коду.
5. Отдельно решить вопрос о fail-closed policy для неприменимого события текущей игры по целевому сценарию.

После этого #187 вполне можно закрыть, сохранив существующие имена, композицию и большую часть маршрутизации. Следующий рефакторинг должен начинаться с нового доказанного затруднения, а не с оставшихся пунктов старого списка кандидатов.
